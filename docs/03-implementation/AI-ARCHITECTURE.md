# TicketChile AI — M7

## Scope and architecture

M7 extends M1–M6 on `astra/ticketchile-v2`. The audited baseline had a disabled public simulator, an opt-in organizer regex parser, M6 current/proposed review, and real capability-scoped event/inventory/finance services. PRD-AI and approved Fase 1B describe a task-oriented simulator and contextual review, not a floating chatbot. Existing 1D components, shared event preview, M3 authority/rates/audit and M6 normal saves remain the foundation.

`lib/ai/model.ts` defines application features and proposal types. `schema.ts` supplies the same closed JSON schema to the provider and the runtime validator. `AIProvider.generate` returns untrusted output and optional usage; `service.server.ts` validates it before storage/return. Feature consumers never invoke a vendor SDK. The implemented replaceable adapter uses OpenAI Responses with `text.format` strict JSON schema, `store:false`, no tools and a fixed HTTPS endpoint. Contract source: [official Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs). Credentials/model access and live schema acceptance remain unverified; no model version is silently chosen.

`AI_PROVIDER=development` is a deterministic rules provider, explicitly labeled LOCAL_RULES, never available in production. It extracts explicit supplied facts and supplies minimal contextual copy for local testing. It does not claim model reasoning. The old nonproduction `ORGANIZER_AI_ADAPTER=local` remains a compatibility configuration; its old API action delegates to the same M7 service. Missing/invalid configuration is unavailable, with manual editing preserved. There are no new dependencies or browser API keys.

## Schemas and trust

Features: event, title, description, shorten, summary, FAQ, SEO, tiers, readiness, analytics, promotion and communication. Each has an explicit field allowlist. Unknown properties, lifecycle/payment/bank/media fields, invalid enum/category, oversized strings/arrays, fractional/negative CLP, excessive stock, invalid dates/timezones/windows and invalid metric references are rejected. Object schemas reject additional properties; nullable model fields represent missing information and are omitted from the patch. At most 12 proposed tiers, CLP integers up to 100,000,000, capacity up to 1,000,000 and per-order quantities 1–10. New tier IDs are generated by the application; tiers are appended inactive. M6 validates the final merged draft, inventory sums, category existence, media ownership, existing sold/held floors and historical price protection again.

Outputs include patch, missing information, warnings, inference/recommendation entries with metric references, and optional draft copy. Summary/SEO fields persist as editable event data; published metadata uses reviewed SEO with existing content fallbacks. No model URL or image field exists. Output is rendered as text/controlled form values, never HTML. Shape validation does not prove factual truth: all generated copy remains a suggestion requiring review. Exact location, schedules, performers and legal/age conditions must be confirmed by the organizer.

## Public flow and secure handoff

`/simulador` performs real asynchronous generation, shows the development/provider label, structured editable fields and tier controls, missing/warning states, shared desktop/mobile event preview and save/account handoff. Failure keeps current client input and the last stored draft; manual creation remains available when the provider is disabled. The shared preview disables inventory fetch and purchase.

`GET/POST /api/ai/simulator` uses same-origin mutation protection and a bounded body. An explicit generation/save starts a random 256-bit, HttpOnly, SameSite=Lax, host-only cookie (`Secure` in production). The database stores only its SHA-256 hash. Draft/proposal content is AES-GCM encrypted with distinct authenticated contexts using M3's data key. No draft ID in a URL grants access; cookie possession is the anonymous capability. Session and proposal expiry is seven days from creation, not indefinitely refreshed by reads/edits. Authentication/register navigation carries no draft payload or token.

Saving while authenticated binds the draft to the exact actor kind/ID. Bound drafts require that actor on read/save/claim. Claim requires the browser capability **and** live tenant-wide `event.edit`, explicit critical-value confirmation, and a current approved/verified/active organization. A row lock serializes claims. Creation, validated normal save, claim consumption and M3 audit commit together; a failure rolls back the new event. The temporary ciphertext is cleared and cookie invalidated after claim. Replay, expiry, foreign account/organization and ID-only access fail. The event is a private DRAFT, never automatically published.

Registration, verification, approval and MFA remain M3 requirements; the simulator does not grant early organizer access. The browser retains its draft through those steps for seven days. Login/registration and organizer shell expose a return link when a draft exists. Users must return from the same browser before expiry; there is no email claim link, cross-device recovery or identity-merging shortcut. A draft saved under a buyer identity cannot be claimed by a different organizer identity; this deliberate separation needs an explicitly designed identity-linking flow if the product later requires one.

## Organizer context and application authority

`POST /api/organizer/events/:id/ai` supports generate/apply/reject. The legacy `POST /api/organizer/events/:id` proposal action uses the same generation service. All event authority is resolved from M3 persisted sessions, live tenant state and current grants, before context assembly and again after a provider response. Provider latency does not freeze authorization. Proposals bind actor, event, base revision and expiration; only that actor can resolve them. Rejection records audit without editing the event.

| Task | Required capability | Provider context |
| --- | --- | --- |
| Event/copy/FAQ/SEO/tiers/readiness/promotion | `event.edit` | Explicit subset of title, description, category, date, city, venue, capacity, access/age or checklist appropriate to the task |
| Analytics | `finance.read` | Five scoped aggregates: verified paid count/gross, review count, sold tickets and assigned capacity; limitations only |
| Communication draft | `attendees.read` | Event title/date/location/access and aggregate issued/check-in counts; no recipient rows |
| Apply a patch | `event.edit` | Original proposal's field allowlist plus organizer edits, passed to M6 normal save |
| Public claim | tenant-wide `event.edit` | Reviewed temporary draft; no event-scoped membership escalation |

The UI has restrained contextual entry points in creation/editor/inventory/readiness, Event Center AI, sales/analytics, promotions and attendees. Review shows current/proposed values, editable suggestions, selected fields and a summary. Applying any selected capacity/tier/date/timezone/location/age field requires `confirmed === true` on the server; changing values in the UI clears confirmation. Existing M6 sold-event critical constraints still apply. Normal save's transaction helper is reused, including revision/inventory locking and audits. Applied/rejected proposals are single-use. Reversal is an ordinary authorized edit of reviewed values, subject to current revision/inventory constraints; no blind rollback of operational state is offered.

There is no AI publish/pause/cancel/refund/settlement/bank/send endpoint, no direct SQL/tool access for the model and no promotion activation. Promotion/communication outputs are editable draft text only; they cannot be applied as arbitrary domain fields. Existing owner lifecycle confirmation stays separate. M8/M9 own later operational mutations.

## Analytics and privacy

Facts are generated by the application from scoped PostgreSQL aggregates, not accepted from the model. UI separates **Hechos**, **Inferencias · hipótesis** and **Recomendaciones · por revisar**, citing allowed metric labels. Every analytical inference/recommendation must cite an available metric key. The current context is cumulative; no conversion, visit funnel, temporal comparison, net/tax, causality or forecast is fabricated. Additional time-series analysis is a future extension with an explicit data contract.

Context assemblers never serialize whole event/tenant/payment/attendee rows into provider input. Password/session/MFA/bank/provider secrets are absent by construction. A best-effort minimizer additionally removes obvious emails, international phone numbers and key patterns from free text. This is not comprehensive DLP; users are instructed not to enter sensitive personal data. No raw prompt is stored or logged. Approved provider data-processing/retention terms and regional requirements remain operator prerequisites; `store:false` is not a promise of zero provider retention.

Prompt instructions are separate from JSON-encoded untrusted user/event data. Embedded text cannot add tools, broaden SQL scope, bypass output allowlists or authorize application actions. There is no unrestricted retrieval or model-side action loop. Schema validation and human review reduce impact but do not guarantee immunity to misleading generated text; adversarial content/model-quality evaluations remain required before broad enablement.

## Rate, cost, retry, observability and failures

Persisted M3 atomic rate counters enforce per-user/session and global hourly budgets before provider invocation. Public generation additionally uses a tight network allowance (four times configured public allowance), including a shared fallback when no trusted ingress IP is configured. Session creation is limited to 20/network/hour. Only an explicitly configured header that ingress overwrites is trusted; arbitrary forwarded headers cannot rotate identities. Network fallback may deny unrelated anonymous users during abuse; configure trusted ingress and distributed capacity before launch.

Client UUID request IDs correlate calls; a durable unique request row prevents concurrent duplicate provider calls. A same-subject/same-input successful retry returns the stored validated proposal. Different input/actor, resolved, expired, failed or still-running requests conflict. There is no automatic provider retry. A user can explicitly retry with a new ID; an earlier timed-out call may have incurred provider charges. Crash-interrupted RUNNING rows never silently reissue a call. Bounded input/context/output, output tokens, streaming response byte limit and abort timeout control resource exposure.

`ai_requests` records feature, provider/model, state/outcome, latency, optional token usage, actor/event and request ID. Prompt identity is an HMAC digest. Successful structured output is encrypted, not written to logs. Console metadata contains correlation/feature/provider/model/latency or rate outcome, without prompt, contact data or exception body. M3 audit records `ai.applied`, `ai.rejected`, and `ai.simulator_claimed` with accepted field names and sensitive confirmation; events and proposal resolution commit atomically. Failures leave event data unchanged and display a generic recoverable error.

Expiry denies reads/applications immediately. Physical ciphertext/metadata deletion requires an operator retention job; no production scheduler is installed by M7. Adopt a reviewed encrypted-data retention policy and key rotation plan before enablement. The simulator clears draft ciphertext immediately on successful claim.

## Server configuration

See root `.env.example`; it contains no credentials. Do not prefix any provider setting with `NEXT_PUBLIC_`.

| Variable | Default / contract |
| --- | --- |
| `AI_PROVIDER` | `disabled`; `development` only outside production; `openai` for real provider |
| `OPENAI_API_KEY` | Server secret, required only for OpenAI adapter |
| `AI_MODEL`, `AI_ALLOWED_MODELS` | Explicit model ID and comma-separated allowlist; no implicit model choice |
| `AI_FEATURES` | Comma-separated application features; unknown values never enable a task |
| `AI_MAX_INPUT_CHARS` | 4000; accepted config 100–8000 |
| `AI_MAX_OUTPUT_TOKENS` | 2500; 256–4000 |
| `AI_TIMEOUT_MS` | 20000; 100–30000 |
| `AI_PUBLIC_HOURLY_LIMIT` | 5; 1–20 |
| `AI_USER_HOURLY_LIMIT` | 30; 1–100 |
| `AI_GLOBAL_HOURLY_LIMIT` | 200; 1–1000, deployment-wide persisted counter |
| `SECURITY_DATA_KEY` | Existing M3 canonical 32-byte base64 encryption/HMAC key |
| `SECURITY_TRUSTED_IP_HEADER` | Existing M3 ingress configuration, never trust client-controlled/appended values |

Configuration outside numeric bounds falls back to conservative defaults. No API selects arbitrary provider URLs/models or overrides budget values. Missing allowed model/key fails closed. Run a small explicitly authorized sandbox contract/quality test after selecting an available model; this milestone performs no live calls and does not need production credentials.
